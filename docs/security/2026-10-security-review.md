## 고친 문제

### 1. 로그인 인증코드 무차별 대입 (위험도: 높음)

① **어떤 문제인가** — 이메일 로그인은 6자리 숫자 코드를 쓰고, 코드 하나당 5번까지만 틀릴 수 있게 돼 있었다. 그런데 요청을 **동시에** 여러 개 보내면 이 5번 제한이 통째로 무시됐다. 또 같은 맞는 코드를 동시에 보내면 1회용 코드가 여러 번 쓰였다.

② **왜 생겼나** — 서버가 "지금까지 몇 번 틀렸나 읽기 → 코드 비교 → 틀린 횟수 +1"을 세 번에 나눠 처리했다. 동시에 들어온 요청들은 모두 "아직 0번 틀림"을 읽고 통과한다.

③ **실제 위험** — 남의 이메일로 코드를 요청한 뒤 짧은 시간에 수많은 추측을 동시에 보내면, 코드 하나로 원래 5번이 아니라 수십~수백 번을 시도할 수 있다. 성공하면 **그 학생 계정에 로그인**해 성적·수강 이력·상담 기록을 볼 수 있다.

④ **해결** — 시도 횟수를 "비교하기 전에 DB 한 문장으로 먼저 차지"하도록 바꿨다(`attempts < 5`일 때만 +1, 실패하면 비교 없이 거절). 코드를 쓸 때도 "아직 안 쓴 코드일 때만" 사용 처리해 한 번만 성공한다. 비교는 시간차로 정보가 새지 않는 방식(`timingSafeEqual`)으로 바꿨다. — `server/services/emailAuthService.js`

⑤ **테스트** — `server/test/emailAuth.bruteforce.test.js`
- 수정 전: 틀린 코드 40개를 동시에 보내자 **40개 모두 비교됨**(상한 5 무력화), 같은 코드 동시 3회 중 여러 개 성공 → 실패.
- 수정 후: 비교는 정확히 5번만, 이후엔 맞는 코드도 거절, 같은 코드 동시 사용은 1번만 성공 → 통과. 정상 로그인 흐름도 통과.

### 2. 인증코드 확인 요청 횟수 제한 없음 (중간)

① 코드 **발송**에는 횟수 제한이 있었지만 코드 **확인**(`POST /api/auth/email/verify`)에는 없었다.
② 확인 단계는 코드당 5회 제한만 믿고 있었다.
③ 1번 문제와 겹치면 위험이 커지고, 단독으로도 무차별 대입 속도를 제한할 장치가 하나뿐이다.
④ 같은 이메일을 대상으로 한 확인 요청을 15분에 20회로 묶었다. 기준을 IP가 아니라 **대상 이메일**로 잡아, 다른 사람 로그인에는 영향이 없다. — `server/routes/auth.js`
⑤ 서버 전체 테스트 통과(정상 로그인·동의 테스트 포함).

### 3. 이메일 주소 검사가 허술함 (낮음~중간)

① `x<a@b.com>`, `a@b.com,c@d.com`, 255자 넘는 값 등이 "올바른 이메일"로 통과했다.
② 검사가 "공백 없고 @가 하나" 정도만 봤다.
③ 메일 발송 서비스는 이런 값을 "표시이름 + 실제 주소"나 "주소 목록"으로 해석할 수 있다. 그 결과 DB에는 이상한 문자열로 계정이 생기고 코드는 다른 주소로 가는 식의 혼선이 생긴다. 실제로 수정 전 코드로 재현해 보니 `x<a@b.com>`이 검증을 통과해 로그인 토큰이 만들어지고 발송 단계까지 갔다(발송 서비스가 거절해 메일은 나가지 않음).
④ 주소 목록·헤더로 해석될 수 있는 문자(`< > , ; : " ' \ ( ) [ ]`, 제어문자)와 254자 초과를 거절한다. — `server/routes/auth.js`
⑤ `security.hardening.test.js`: 수정 전 실패(500), 수정 후 모두 400 `INVALID_EMAIL`.

### 4. AI 호출 비용 남용 (중간~높음, 비용 측면)

① 챗봇(하루 20회 제한)과 달리 **진로 탐색의 AI 호출 4개 라우트에는 횟수 제한이 전혀 없었다.** 또 챗봇 질문·진로 대화 입력의 **길이 제한이 없었고**, 챗봇의 하루 20회 제한도 동시 요청으로 넘을 수 있었다.
② 진로 탐색은 나중에 추가되며 한도 장치가 빠졌다. 하루 한도는 "오늘 몇 번 했나 세기 → 저장"이 따로라 동시 요청이 모두 통과했다.
③ 로그인만 하면(이메일만 있으면 누구나 가입 가능) 스크립트로 Claude·Voyage API를 무제한 호출해 **API 요금을 크게 발생시킬 수 있었다.** 요청 하나에 약 100KB짜리 질문을 넣을 수도 있었다.
④
- 진로 탐색 AI 라우트: 사용자당 시간당 120회(정상 상담은 한 번에 10~20회 수준). 대화 입력 2,000자, 고정 질문·답변 각 1,000자·최대 10개, 직업명 200자. — `server/routes/career.js`
- 챗봇: 질문 2,000자, 문자열만 허용. 한 사용자가 답변을 기다리는 동안 보낸 추가 질문은 429 `CHAT_REQUEST_IN_PROGRESS`로 거절(동시 요청으로 하루 한도를 넘는 문제 차단). — `server/routes/chat.js`
- 숫자들은 각 파일 상단 상수라 쉽게 조정할 수 있다.
⑤ `security.hardening.test.js`: 수정 전 긴 입력이 그대로 통과(500/AI 단계 진입), 수정 후 AI를 부르기 전에 400. 서버 전체 테스트 통과.

### 5. 입력 타입 검사 부족 (낮음~중간)

① 여러 API가 값의 **타입**을 확인하지 않았다. 예: 닉네임에 숫자를 보내면 서버 오류(500), 쿼리스트링 `?year[x]=1`, `?year=1&year=2`, 없는 학과 id나 3000학번으로 온보딩, 과목 점수에 객체를 넣는 경우 등.
② 데이터베이스 라이브러리(mysql2)는 배열·객체를 받으면 SQL 조각(`a, b` 목록이나 `` `x` = 1``)으로 펼친다. 값 자체는 안전하게 이스케이프되지만, 개발자가 의도하지 않은 조건문이 만들어진다.
③ 다른 학생 데이터가 새는 경로는 확인되지 않았다(모든 질의에 본인 id 조건이 따로 붙어 있음). 다만 오류를 일부러 일으키거나, 잘못된 학번·학과가 저장돼 졸업요건 진단이 틀어질 수 있었다.
④
- 모든 API에서 쿼리스트링 값이 문자열 하나가 아니면 400 `INVALID_QUERY`. — `server/middleware/security.js`
- 프로필(닉네임·학번·상담 횟수·휴학 학기), 온보딩(학과 존재 여부·학번 범위), 내 과목(연도·학기 코드·과목명 길이·점수·한 번에 가져오기 500행) 검사 추가. — `server/services/inputValidation.js`, `routes/me.js`, `routes/onboarding.js`, `routes/myCourses.js`
⑤ `security.hardening.test.js`: 수정 전 500/엉뚱한 단계로 진행, 수정 후 400. 실제 화면 흐름(과목 추가 → 성적 입력 → 목록 → 삭제, 카탈로그 검색)도 브라우저에서 정상 동작 확인.

### 8. 브라우저 보안 헤더 없음 (중간)

① 화면(Vercel)과 API(Railway) 응답 모두 보안 헤더가 없었다. 운영 백엔드에 직접 요청해 확인했다(`/api/version` 응답에 보안 헤더 없음).
② 따로 설정한 적이 없었다.
③ 다른 사이트가 우리 화면을 투명한 iframe으로 덮어 클릭을 가로챌 수 있고(클릭재킹), 나중에 화면에 XSS 버그가 하나라도 생기면 이를 막아 줄 두 번째 방어선(CSP)이 없다. 학사 정보가 담긴 API 응답이 브라우저 캐시에 남을 수도 있었다.
④
- API: `nosniff`, iframe 금지, 가장 좁은 CSP, `Cache-Control: no-store`, 운영에서만 HSTS. — `server/middleware/security.js`, `server/app.js`
- 화면: `client/vercel.json`에 CSP(스크립트는 자기 도메인만, 인라인 스크립트 금지), iframe 금지 등. 이를 위해 `index.html`의 인라인 테마 스크립트를 `client/public/theme-init.js`로 옮겼다(동작 동일).
⑤ 빌드한 화면을 `vercel.json`과 똑같은 헤더로 띄워 브라우저에서 확인: 홈·과목 관리·졸업요건·커뮤니티·진로 탐색 화면에서 **CSP 위반 0건, 실패한 API 요청 0건.** 웹폰트(Pretendard)와 테마 적용도 정상. 일부러 인라인 스크립트를 넣어 보니 **차단됨**. 단, Vercel 실제 배포에서 헤더가 붙는지는 배포 후 한 번 더 확인해야 한다(미리보기 배포에서 개발자도구 Network 탭으로 확인).

### 10. 알려진 취약 라이브러리 (중간/낮음)

① `npm audit`에서 `source-map-js`(서비스 거부, 높음)와 `shell-quote`(명령 주입, 치명)가 나왔다.

④ 각각 1.2.2, 1.12.0으로 올렸다(`package-lock.json`, 호환되는 패치 버전).
⑤ 운영 의존성 기준 `npm audit` 취약점 0건. 남은 것은 아래 "남은 위험" 참고.

## 결정이 필요한 문제 (임의로 바꾸지 않음)

### A. IP 기준 횟수 제한의 실효성과 백엔드 직접 접속

- **현황** — 화면은 Vercel이 `/api/*`를 Railway로 넘기는 구조인데, 서버는 `trust proxy 1`로 "바로 앞 프록시 한 단계"만 믿는다. 그러면 서버가 보는 접속자 IP가 **학생 IP가 아니라 Vercel 서버 IP일 가능성**이 있다. 그 경우 기존 IP 기준 제한(인증코드 발송 10분 5회, PDF 업로드 10분 10회)이 **모든 사용자에게 공유**된다. 한 사람이 5번 요청하면 그 10분 동안 다른 학생 모두가 로그인 코드를 못 받을 수 있다. 또 Railway 주소(`web-production-afdfe.up.railway.app`)로 **직접 접속이 된다**(확인함). 그래서 Vercel에만 거는 설정은 우회된다.
- **확인 못 한 것** — 운영에서 `req.ip`가 실제로 무엇으로 찍히는지는 운영 로그를 봐야 안다.
- **선택지**
  1. *(추천)* 운영에서 `req.ip`를 한 번 로그로 확인한다. Vercel IP로 찍히면 IP 기준 제한을 **이메일·사용자 기준**으로 바꾼다. 이번에 새로 넣은 제한은 이미 사용자/이메일 기준이다. 장점: 다른 학생을 막는 부작용이 없다. 단점: 같은 IP에서 여러 이메일로 공격하는 경우는 DB의 이메일별 발송 제한(5분 쿨다운·하루 8회)에만 의존한다.
  2. `trust proxy` 단계 수를 늘려 실제 학생 IP를 쓴다. 장점: 코드 변경이 작다. 단점: Railway에 직접 접속하는 사람은 `X-Forwarded-For`를 위조해 제한을 피할 수 있다. 직접 접속 차단과 함께 해야 의미가 있다.
  3. Railway 직접 접속을 막는다(Vercel → Railway 사이에 비밀 헤더 확인 등). 장점: 우회 경로가 사라진다. 단점: Vercel rewrite는 요청에 임의 헤더를 붙이기 어려워 구조 변경(Vercel Edge Function 등)이 필요하다. `/api/version`처럼 직접 확인하던 습관도 바뀐다.

### B. 메일 중계 주소로 누구나 메일을 보낼 수 있음

- **현황** — 커뮤니티 신청이 수락되면 학생에게 `…@relay` 중계 주소가 생기고, 그 주소로 온 메일은 **보낸 사람이 누구든** 상대 학생에게 "ONE Student 커뮤니티 매칭을 통해 전달된 메일입니다" 양식으로 전달된다(첨부파일 포함). 본문 HTML 정리와 외부 이미지 차단은 잘 돼 있다.
- **위험** — 중계 주소가 유출되면(화면 캡처 공유 등) 제3자가 우리 서비스 이름을 달고 피싱 메일·악성 첨부를 학생에게 보낼 수 있다.
- **선택지**
  1. 보낸 사람이 "그 매칭의 상대 학생 실제 이메일"일 때만 전달. 장점: 가장 확실하다. 단점: 가입 이메일이 아닌 다른 주소로 보내면 전달되지 않는다(안내 필요).
  2. 첨부파일만 막거나 실행 파일 확장자만 거르고 나머지는 지금처럼 둔다. 장점: 사용성 유지. 단점: 피싱 본문은 여전히 가능하다.
  3. 현행 유지 + 안내 문구에 "모르는 사람이 보낸 메일일 수 있음"을 추가한다.

### C. 운영 환경 설정 (저장소에서 확인 불가)

Railway 대시보드에서 다음을 확인해야 한다. 코드는 이 값들이 맞다는 전제로 안전하다.
- `NODE_ENV=production` — 아니면 세션 쿠키 `secure`, HSTS, 아래 `SESSION_SECRET` 검사가 모두 꺼진다.
- `SESSION_SECRET` — 길고 무작위한 값이어야 한다. 없으면 코드의 기본값(`wku-default-secret`)으로 서명돼 **누구나 아무 학생으로 로그인한 쿠키를 만들 수 있다**(production이면 서버가 아예 안 뜨게 막혀 있음).
- `RESEND_WEBHOOK_SECRET` — 없으면 웹훅이 전부 거절된다(위조 메일 전달은 불가함을 확인).

## 점검했고 문제가 없던 부분

- **SQL 인젝션**: 모든 질의가 `?` 자리표시자로 값을 바인딩한다. 문자열을 이어 붙이는 곳은 코드에 고정된 컬럼·테이블 이름뿐이다.
- **남의 데이터 조회·수정(IDOR)**: 내 과목·대화·진로 세션·커뮤니티 글/신청/신고·문의 모두 본인 id 조건으로 조회·수정한다. 비공개 글은 작성자와 수락된 신청자만 본다.
- **관리자 권한**: 관리자 API는 매 요청마다 DB에서 role을 다시 확인한다. 화면에 내려가는 role은 표시용일 뿐이다. 프로필 수정으로 role을 바꿀 수 없다.
- **세션**: 로그인 시 세션 id 재발급(세션 고정 방지), `SameSite=Lax`, Google 로그인 `state` 검증, 계정 삭제 전 재인증.
- **챗봇 답변 표시**: HTML을 직접 넣지 않고 React 요소로만 그려 XSS가 생기지 않는다. 화면 전체에 `dangerouslySetInnerHTML` 없음.
- **RAG 검색 대상**: 저장소의 규정 문서만 임베딩한다. 사용자가 쓴 글이 다른 사람의 AI 답변 근거로 들어가는 경로는 없다.
- **파일 업로드**: PDF는 메모리에서만 처리하고 디스크에 저장하지 않는다. 10MB 제한, 횟수 제한, AI 호출 학기당 한도가 있다.
- **메일 중계 웹훅**: 서명(svix)을 검증한다. 비밀값이 비어 있어도 위조 요청이 거절됨을 확인했다.
- **비밀값**: 저장소와 git 이력에 API 키·`.env`가 들어간 적이 없다(`.env.example`만 있음).

## 남은 위험 (낮음, 이번에 고치지 않음)

- 계정을 삭제해도 **다른 기기에 남은 로그인 세션**은 즉시 지워지지 않는다(대부분의 API는 계정이 없으면 401이라 실질 영향은 작음).
- 챗봇 "동시 요청 막기"는 서버 프로세스 하나 안에서만 유효하다. 서버를 여러 대로 늘리면 Redis 같은 공용 저장소가 필요하다.
- `npm audit`의 남은 항목은 로컬 개발 도구(`nodemon` → `braces`)뿐이다. 운영에는 포함되지 않으며, 자동 수정은 `nodemon`을 아주 옛 버전으로 내려 하지 않았다.
- GitHub Actions의 `vercel@latest`, 액션 버전이 고정돼 있지 않다(공급망 위험). 버전 고정을 권장한다.
- `/api/version`이 운영 커밋 해시를 공개한다(의도된 기능, 정보 노출은 작음).
